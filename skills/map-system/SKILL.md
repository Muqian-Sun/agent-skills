# 系统由哪些代码组成

**这个技能只做一件事：把范围划出来。** 深入讲某一个仓库是 `explain-project` 的事，讲完这张表就交棒过去。

**先划范围，再讲内容。** 新人手上通常只有一个仓库地址，于是默认"这个仓库 = 这个系统"。这个默认在两个方向上都会错，而且错法相反：

- **系统比仓库大**：后端由好几个仓库拼成，他手上这个只是一块。照一个仓讲，"全流程"是断的——请求从哪儿来、去哪儿，答案在别人仓里
- **仓库比系统大**：一个仓塞着十几个项目，只有一两个跟这条业务线有关。照整个仓讲，一大半跟他无关，还容易把没人维护的老项目当成现役系统

这两种错**读得更仔细也避不开**——是范围问题，不是深度问题。

## 从他手上那一个入口倒推

新人手里一般只有一样东西：一个仓库地址、一个服务名、一个域名或接口地址、或者一条告警。从这一个点往两个方向扩。

**往外扩——找出系统的其他部分：**

- **出站配置**：host / endpoint / url / appkey 类配置项指向的都是仓库外的依赖。通读一遍配置和环境变量，比读任何架构文档都快
- **MQ topic / 队列名**：名字里带别的服务名的（`xxx_file_transfer` 这种），对面多半是兄弟仓库
- **注释和常量里点名的服务**：拿产品线的服务名前缀 grep 一遍往往能捞到
- **org / team 的仓库列表**：`gh api /orgs/<org>/teams/<team>/repos`，一眼看清这条产品线有几个服务

**往内收——判断这个仓里哪几块才属于这个系统：**

- **构建描述符有几个**：多个 `pom.xml` / `go.mod` / `Cargo.toml`、`package.json` 的 workspaces、`BUILD` 文件——一个通常对应一个可独立部署的单元
- **流水线里真正部署出去的是哪几个**：`.gitlab-ci.yml` / `Jenkinsfile` / `Dockerfile*` / `k8s/` 里的服务名和镜像名是最硬的证据，没进流水线的目录多半是死的
- **哪些子目录有自己的入口**（下一节侦察表里那几种，逐个子目录看一遍）
- **`CODEOWNERS` / `OWNERS`**：哪些目录归你们团队
- **`git log` 近一年动过的才是活的**：几年没提交的别当现役系统讲，但要在组成表里标"已停更"，免得新人自己翻到误以为是主线
- **拿线上服务名 / 镜像名回仓库里搜**：能直接锁定它由哪个子目录构建

## 产出：一张系统组成表

这是新人第一眼最需要的东西——他得先知道自己站在哪。

| 仓库 / 子项目 | 属于这个系统吗 | 本次聚焦吗 | 角色 | 我读得到吗 |
|---|---|---|---|---|
| `order-api`（你手上这个） | 是 | **聚焦** | 对外 HTTP 入口 | ✅ 已读 |
| `order-worker` | 是 | 否 | 异步履约，消费 MQ | ✅ 已 clone |
| `pay-svc` | 是 | 否 | 支付，网关直接转给它，不经过 order-api | ✅ 已 clone |
| `inventory-svc` | 是 | 否 | 库存扣减，别的团队维护 | ❌ 读不到，只能当外部依赖讲接口 |
| `risk-engine` | 是 | 否 | 风控，别的团队维护 | ❌ 读不到 |
| 同仓 `legacy-crm/` | **否** | 否 | 三年没提交的老项目 | — 完全不读 |

表里每一行都要说清**凭什么这么判**（在流水线里 / 有自己的 main / CODEOWNERS 归谁 / 近一年有没有提交），按纪律 2 标好证据级别。判不准的行标成"推断"并记进待确认清单，别硬塞进"是"或"否"。

## 「范围」和「聚焦」是两件事，别混着说

这张表把代码分成三层，后面每个阶段该读到什么深度，都以这三层为准。**这两个词在导览里含义固定，不要换着用**：

| 层 | 判据 | 后面怎么对待它 |
|---|---|---|
| **范围内 + 聚焦** | 属于这个系统，且是本次要讲透的那一块 | 交给 `explain-project` 走完整套导览 |
| **范围内 + 不聚焦** | 属于这个系统，但这次不深挖（兄弟仓、别的团队维护的服务） | 只给轮廓和契约：读得到的给顶层目录树，读不到的只讲接口契约。**不深追它的内部实现** |
| **范围外** | 不属于这个系统（同仓的无关项目、别的产品线） | 一行都不读，也不出现在后面任何一张表和图里 |

最容易搞错的是中间那层：它**在范围内**，所以链路跨到它那儿时必须讲清楚去了哪儿、传了什么；但它**不聚焦**，所以不要跑去把它的代码也通读一遍。"跨出边界要标注"和"不要在多个仓库间横跳"说的正是这一层的两面，不矛盾。

**读不到兄弟仓库怎么办**——权限没开、跨团队、代码在别的平台，都很常见。能 clone 就 clone，有代码搜索就搜；拿不到就当**外部依赖**讲，只讲契约：调它什么、传什么、返回什么、失败了会怎样——这些从你这边的调用方代码里读得出来。同时按三件套记进待确认清单。**不要假装它不存在**，更不要凭服务名猜它内部实现。

## 讲完这张表，确认聚焦范围

表是廉价的，深讲是贵的。表给完问一句：

> "这个系统由这几块组成，你手上的是 X。接下来我按 X 往下讲，还是先把跨服务的主流程串一遍？"

不回答就按默认走：**聚焦他那个仓，交给 `explain-project` 深入；范围内不聚焦的给轮廓和契约；范围外的不碰**——既有能上手的深度，也有系统全貌的骨架。

## 判断依据要标清楚（与 explain-project 同源，改一处要改两处）

组成表里每一行的判断，按可信度标级别，让人知道哪些能直接信：

| 级别 | 依据 | 怎么说 |
|---|---|---|
| 实测 ⭐ | 打过真实接口 / 跑过真实流程 | 直接陈述 + 贴响应片段。与代码推断冲突时以实测为准 |
| 可信 | 读到了代码 | 直接陈述 + `文件:行号` |
| 参考 | 只有文档/注释 | 标明出处 + "未在代码中验证" |
| 推断 | 我根据模式推的 | 说明推断依据 + 给出验证方法 |

**"代码里没有"有两种可能——你没找到，或者它不在这个仓库。别默认是前者。** 默认前者，就会一直在错的仓库里翻；把后者摆上台面，才会想到去问"是不是还有别的服务"。

## 待确认清单（与 explain-project 同源，改一处要改两处）

判不准的行不要硬塞进"是"或"否"，记进清单交给对方去问人。**区分两种，处置方式正相反**：

- **查不到**（不在任何我能访问的地方：别的团队的仓库、外部系统的口头约定）→ 写进清单，**必须附上"我查过哪些地方"**
- **没查**（我能查但这次没做）→ **自己去查，不许写进清单**。把自己能解决的事塞给别人，是在占用比你贵得多的时间

清单里每条写三件事，缺一条就没法直接拿去问人：**现象**（看到了什么，附 `文件:行号` 或实测响应）、**我查了什么**、**卡在哪**（具体哪一步推不下去，以及我猜是什么，标明是猜的）。

## 产出放哪里（与 explain-project 同源，改一处要改两处）

组成表是要给人反复回看的，别只打在对话里：**有 artifact 工具就写进 artifact**，没有就写成 Markdown 文件放在**仓库之外**（兄弟目录、home 下的笔记目录、临时目录），把绝对路径告诉用户。

**禁止把它写进仓库里**——这是个人笔记不是项目资产，极易被误提交，还会污染别人的 `git status`。加 `.gitignore` 不是解法，那也是在改仓库。

如果接下来要交给 `explain-project`，**用同一份产出**，让它往后追加，不要另起一份。

## 反面模式

- ❌ 拿仓库边界当系统边界：把"仓库里没有"当成"系统里没有"，或把一个仓里十几个项目全讲一遍
- ❌ 组成表只列仓库名，不说凭什么判定它属于这个系统
- ❌ 读不到的兄弟仓库就当它不存在，或者凭服务名猜它内部怎么实现
- ❌ 划完范围不交棒，自己接着往下深入讲某一个仓——那是 `explain-project` 的活
- ❌ 把组成表写进被分析的仓库里

## 划完之后

把表和三层定界交给用户，确认聚焦哪一块，然后**调用 `explain-project`，把这份产出和聚焦结论一起带过去**。它会在你划定的范围内走完整套导览：项目定位 → 代码地图 → 对外接口 → 分层架构 → 核心链路 → 数据模型 → 一次真实请求 → 技术方案 → 关键源码。

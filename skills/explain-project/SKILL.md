# 带新人过一遍这个仓库

## 这个技能要解决什么

听众是**刚进组的研发**：他会写代码，但对这个项目一无所知。他的真实困境不是"没有文档"，而是**已有的一切都默认你已经懂了**：文档用黑话解释黑话，代码没有入口线索，老员工三句话带过的地方全是坑。

所以本技能的产出是**一次分阶段、可追问、能听懂的系统导览**：内容分阶段写进一份 artifact（或落盘文件），对话里带着他一段段走、随时停下来答疑。它同样是一份文档，但不是那种一次性甩过去、写给老员工看的架构文档。

判断标准只有一个：一个昨天刚入职的人，听完能不能说清**一次真实请求落在这个仓库的哪段代码上、数据怎么流、以及哪几跳跨出了这个仓库去了哪儿**。

最后半句容易被忽略：讲透一个仓不等于让他理解了整条链路，凡是跨出边界的跳都要点名去了哪个服务——边界本身由 `map-system` 划定，这里只负责讲清楚跨出去的那几跳。

## 四条贯穿全程的纪律

**1. 先读够再开口。** 只读了几个文件就总结架构，会给出看似合理实则错误的结论——而新人**没有能力分辨你错在哪**，误导成本远高于说"我不确定"。覆盖度自检：如果某个体量不小的目录你一行都没看过，要么去看，要么在讲之前明确说"这块我没覆盖"。

**2. 实测 > 代码 > 文档。对外接口，讲之前先打一次。**

README、Wiki、接口文档、需求文档、代码注释都会过期，而且**过期得悄无声息**——写的人不会回来更新，但代码一直在跑。新人被过期文档误导，往往要一两周才发现。所以文档只当线索，结论从代码来。

但代码之上还有一层它读不到的事实：**"代码里注册了这条路由"不等于"线上走这条路由"**——中间可能有网关改写、被别的服务截胡、或者这条路由早就 500 着没人管。读多少代码都推不出来，只能打一次才知道。更麻烦的是**正推会得出反的结论**：看到仓库注册着 `/foo/v1/bar` 就以为客户用它，实际客户用的是网关转过来的 `/v1/bar`——新人照错地址调试，白花好几天。

**只打安全的那种**：读接口、健康检查、故意打错参数或打不存在的路径，这些都行；写入、删除、支付、发消息这类有副作用的不要真打——问用户要测试环境，拿不到就只讲推断。

**打不了也要说清楚。** 内网、没凭据、本地跑不起来是常态，不是失败：明说"这条我没能实测"，结论退回"推断"级，按三件套记进待确认清单。最糟的是打不了却不吭声，让新人以为验证过。

- 任何结论**优先从代码得出**，并附 `文件:行号`
- **只有代码里确实拿不到时**（比如历史背景、当初为什么这么设计、外部系统的约定）才引用文档或注释
- 引用参考来源时**必须显式标注来源并声明不可信**，例如："据 README 说 X（未在代码中验证，可能已过期）"、"注释写的是 Y（注释未必与实现同步）"
- 代码与文档矛盾时**以代码为准**；**实测与代码推断矛盾时以实测为准**。两种矛盾都要明确指出来——这对新人价值极高

每个关键结论按可信度分四级标注，让新人自己知道哪些能直接信（**这张表与 `map-system` 同源，改一处要改两处**）：

| 级别 | 依据 | 怎么说 |
|---|---|---|
| 实测 ⭐ | 打过真实接口 / 跑过真实流程 | 直接陈述 + 贴响应片段。与代码推断冲突时以实测为准 |
| 可信 | 读到了代码 | 直接陈述 + `文件:行号` |
| 参考 | 只有文档/注释 | 标明出处 + "未在代码中验证" |
| 推断 | 我根据模式推的 | 说明推断依据 + 给出验证方法 |

**3. 没读到就不要当事实说。** 可以给推断，但必须按上表标成"推断"；不能把脑补讲成陈述句。最常见的一种脑补是**拿框架通识替代项目实情**——不要说"Spring Boot 一般是这样"，要说"这个项目实际是这样，见 xxx"。实在没读就直说"这块我没看，需要的话我去读"。

**4. 分段交付，不要倾倒。** 每讲完一个阶段就更新一次产出，然后在对话里停下来问一句"这块清楚了吗，要不要展开某处"，等回应再继续下一阶段。除非用户明确说"一次性给我全部"。

分段指的是**交付节奏**，不是让内容写得少：artifact 里该写多细写多细，新人回头要靠它复习；节制的是一次推给他多少。

## 讲述的主线：需求 → 功能 → 代码

先有业务需求，才有功能，才有代码。所以导览的顺序就顺着这条链往下走，每一段都是上一段的下游：

**项目定位与业务目标 →（代码地图：先给一张坐标系）→ 对外接口 → 分层架构 → 核心链路 → 数据模型 → 具体请求 → 技术方案 → 源码**

前提是范围已经划定（`map-system` 的活）。范围划错，后面读得再细都是白读。

倒过来讲——从代码、从模块、从技术栈讲起——新人只能记住一堆孤立名词，因为他不知道这些东西是为了满足谁的什么诉求才存在的。

**阶段四到阶段六一路都是业务视角**：讲流程走向、讲数据长什么样、讲一次真实请求。而**从阶段三起就不解释技术选型了**——分层图只说有哪些组件、谁调谁，为什么这么选留到阶段七；源码留到阶段八。

这个分界要守住，理由有两条，也是下面每个阶段结尾都会再点一次这条界的原因：一是业务线索被技术细节打断一次，新人就得重新接一次；二是他这会儿还没有能挂住这些细节的钩子，讲了也是白讲。

## 开讲之前：自己先侦察一遍

**先确认前置条件：范围划了没有。**

这个技能讲的是**一个仓库**——但仓库边界不等于系统边界。开讲之前必须先知道：这个系统由哪些仓库 / 子项目组成、本次聚焦哪一块、哪些是范围内但不深挖的兄弟仓。

- **还没划过** → 先用 `map-system` 技能划出来，拿到系统组成表和聚焦结论再回来
- **已经划过 / 用户明确只要这一个仓** → 直接往下走，但心里要清楚哪几跳会跨出边界

然后按这个顺序走：

1. **建产出**——按下一节把 artifact 或落盘文件建好（`map-system` 已经建过就沿用同一份），此时还没对用户说一个字
2. **给导览大纲**——阶段零到阶段八各讲什么、预计多少内容
3. **扫下面这张侦察表**，然后依次讲阶段零到阶段八

下面这张表**不对用户输出**。**不要一上来就问用户问题**——他找你就是因为他也不知道。先自己看一遍：

| 看什么 | 能得到什么 |
|---|---|
| 构建文件（pom.xml / package.json / go.mod / requirements.txt）、目录树 | 技术栈、模块划分、依赖了哪些外部系统（可信） |
| README、Wiki、产品文档、需求文档 | **只当线索用，不当结论用**：业务背景的主要来源，但可能已过期 |
| **显式声明的入口**：main / Application / 路由注册 / controller 注解 / *.proto / openapi 定义 | 一眼能找到的那部分入口 |
| **最容易漏看的入口**：MQ 消费者、定时任务 / Job、CLI、Webhook 回调、管理后台、对外 SDK | 没人会主动提，却常常是业务核心。两行合起来才是阶段二要交付的入口全集 |
| DB migration / DDL / ORM entity；以及 Redis / ES / 对象存储 / MQ 消息体的客户端依赖和 key 常量 | 业务真相的最可靠来源，比注释可靠；后半截还能看出同一份数据一共存了几份 |
| 测试与 fixture | **真实的请求参数**，阶段六的素材 |
| 配置文件、环境变量、feature flag | 运行时行为的开关：哪些逻辑按环境/灰度走不同分支。出站依赖那部分 `map-system` 已经扫过，不用重复 |

这张表扫的全是**聚焦那个仓库的内部**——范围没定就不知道该扫哪些目录，所以它排在划范围之后。

一句话贯穿全程：**"代码里没有"有两种可能——你没找到，或者它不在这个仓库。别默认是前者。** 默认前者，就会一直在错的仓库里翻；把后者摆上台面，才会想到去问"是不是还有别的服务"。

扫完这张表，你手上就有讲完全程所需的全部素材了。

整场导览**你只主动问一个问题**（以下都不算在内：纪律 4 的每段确认、阶段二为实测索取真实地址或测试环境、阶段四挑链路时的选择题）：

> "你接下来主要负责哪一块？我可以把那条链路讲得更细。"

跟着导览大纲一起问。用户不回答也没关系，按默认深度继续。

### 怎么在有限时间里"通读"圈定范围内的代码

**先按 `map-system` 的组成表把范围圈出来**——不在范围内的子项目和兄弟仓库，一行都不用读。范围之内也不是逐行读完，而是**先骨架后血肉**：

1. 目录树 + 构建文件 → 建立模块心智图
2. 找到全部入口 → 列成清单
3. 从每个**核心**入口顺着调用往下追，直到落到 DB / RPC / MQ 为止，记录调用链
4. 读 DDL 和实体，连同 Redis / ES / 对象存储里那几份，把数据模型独立还原一遍
5. 拿调用链和数据模型互相验证，对不上的地方就是你理解错了或代码有坑——两种都值得讲

## 产出放在哪里：开讲之前先定好（与 `map-system` 同源，改一处要改两处）

**这件事在开讲之前做完，不是收尾工作。** 图能不能渲染直接决定新人看不看得懂，而对话窗口（尤其是终端）大多不渲染 Mermaid——把源码直接打在对话里，等于什么都没给他。

**优先级 1：有 artifact 工具 → 讲解内容写进 artifact。**

- **开讲之前就先把 artifact 建好**（`map-system` 建过就接着用它那份），阶段零的内容直接写进去，对话里只说一句"第一部分放好了，看完告诉我"
- **整场导览自始至终只用这一个 artifact**，每讲完一个阶段就更新它，不要每个阶段新建一个
- **所有 Mermaid 图必须在 artifact 里**，对话里一行 Mermaid 源码都不要出现。既没有 artifact 工具、也没法写文件时，才改用带缩进的 ASCII 结构图
- 对话里留给：一两句导语、纪律 4 的确认提问、用户追问时的即时回答

**优先级 2：没有 artifact 工具 → 写成 Markdown 文件，放在仓库之外**（兄弟目录、home 下的笔记目录、临时目录）。同样是开讲前建好、一路追加，写完把**绝对路径**告诉用户，让他用能渲染 Mermaid 的编辑器打开。

不管落在哪里，**结构都照搬阶段零到阶段八的顺序**，末尾加一节**"待确认清单"**（见下）。

**禁止把这份文档写进仓库里**——仓库根目录、`docs/`、`.notes/`、任何位置都不行：

- 这是个人学习笔记，不是项目资产，极易被误提交进版本库
- 污染别人的 `git status` 和 diff，给 review 添麻烦
- 加 `.gitignore` 不是解法，那也是在改仓库

唯一例外：用户**明确要求**把它作为项目文档提交进仓库。这时先确认放哪个目录、要不要走 review，再动手。

### 末尾那一节叫"待确认清单"，不叫"我没覆盖的部分"（与 `map-system` 同源，改一处要改两处）

**这一节从第一个阶段就开始攒，不是收尾才补。** 走一遍必然积下一堆"我不确定"，它们正是新人第一周最该带去问人的东西——前提是问题写得够具体，否则他只能转述成"这块我没看懂"，问了也白问。

攒的时候**区分两种，处置方式正相反**：

| 类型 | 判据 | 怎么办 |
|---|---|---|
| **查不到** | 不在任何我能访问的地方：业务目标、当年为什么这么设计、外部系统的口头约定、别人仓库里的实现 | 写进清单让新人去问人。**必须附上"我查过哪些地方"**，否则对方第一反应就是"你搜过吗" |
| **没查** | 我能查但这次没做：某个目录没读、某个接口没打、某张表没看 | **自己去查，不许写进清单。** 把自己能解决的事塞给别人，是在占用比你贵得多的时间 |

分不清属于哪种，就默认按"没查"处理——先去查一次，查完还是不知道，它自然就变成"查不到"了。

这和纪律 1 的"这块我没覆盖"不冲突，两者分工不同：**没覆盖是在正文里当场坦白**（让新人知道这段内容有边界），**待确认清单只收查不到的**（让他拿去问人）。没查的东西两边都不该出现——它该被你查掉。

清单里每条写三件事，缺一条就没法直接拿去问人：

- **现象**：我看到了什么，附 `文件:行号` 或实测响应片段
- **我查了什么**：读了哪些代码、打了哪些接口、翻了哪些文档、问过哪些搜索
- **卡在哪**：具体哪一步推不下去，以及我猜是什么（标明是猜的）

只写"这块不太清楚"是无效的——新人拿着它没法开口。

## 阶段零：这个项目是什么，为谁解决什么问题

范围划定之后，**这里是整场导览在业务上的第一句话，其余所有内容都挂在它下面。** 不知道项目定位就去看代码，新人只会一脸懵：每个类都看得懂，合起来不知道在干嘛。

讲清这七件事：

1. **一句话说清它是干嘛的。** 讲不出这一句，说明你自己还没读懂，回去继续读，别硬讲
2. **它在系统组成表里的位置**（`map-system` 的产出）：上游是谁在调它、下游它依赖谁、它从谁手里接活、把结果交给谁。表里其余几块各自干什么，这里一句话带过即可——新人要的是知道自己这块卡在整条链的哪一环
3. **服务什么业务目标 / 看什么指标**：GMV、履约时效、风控拦截率、审核通过率……这决定了代码里哪些逻辑是"不能动的"
4. **使用者是谁**：C 端用户、商家、内部运营、还是其他团队的系统。使用者不同，代码里的取舍就完全不同
5. **如果这个服务挂了会怎样**——理解一个系统重要性最快的方式，也直接告诉新人哪些改动要小心
6. **边界：它不做什么。** 新人最常见的误解就是把邻居系统的职责算到这个项目头上，提前划清能省掉大量困惑
7. **演进阶段**：新建系统 / 稳定运行的成熟系统 / 正在被替换或下线的老系统。这决定新人该抱什么心态去看那些"写得很怪"的代码

**这些信息从哪来（严格遵守纪律 2）：**

- **代码能给的**：服务名、领域模型命名、对外接口集合、依赖的上下游服务、表名——从这些能相当可靠地反推出业务范围和边界
- **代码给不了的**：业务目标、指标、组织背景、历史演进。这些只能从 README / 产品文档 / 需求文档 / 提交记录里拿，**必须标注"据文档说，未在代码中验证"**
- **都拿不到时**：把从代码反推的结论说出来、标为推断，并**按待确认清单的三件套记下来**——这本来就是新人第一天该问的问题，帮他整理成能直接开口问的样子，比编个答案有价值得多

讲完停一下。定位没对齐就往下走，后面全是白讲。

## 阶段一：代码地图——带注释的目录树

先给一张**代码地图**再讲别的。理由很实际：从下一步起你说的每个接口、每个类、每张表都带一个路径，没先见过骨架，这些路径对新人就是一串无意义字符。目录树是**坐标系**不是内容，所以它排在业务内容前面并不违背主线。

用带注释的目录树，每一行后面跟一句人话，比任何架构图都更快让人找到东西：

```text
src/
├── api/                  接口层：所有 HTTP 入口都在这，一个业务域一个 Controller
│   ├── order/            订单相关接口 ← 你要改的下单接口在这
│   └── user/             用户接口
├── service/              业务层：核心逻辑都在这，改需求 90% 的时间待在这里
│   ├── order/            下单、取消、改价的业务编排
│   └── inventory/        库存扣减（注意：真正的库存服务在另一个仓库，这里只是调用方）
├── repository/           数据层：一个类对一张表，不写业务逻辑
├── job/                  定时任务，容易被漏看，但对账逻辑在这
├── consumer/             MQ 消费者，异步链路的入口
└── common/               工具和常量，枚举值和状态码在 common/enums
resources/
└── db/migration/         建表和变更脚本，看表结构以这里为准
```

写目录树的几条要求：

- **只列到有意义的那一层就停**，不要把每个文件都铺出来，新人需要的是找得到方向而不是清单
- 注释写"**这里放什么、什么时候会来改它**"，不要写"订单模块"这种同义反复
- **标出容易踩坑的目录**：名字看不出是入口的（`job/`、`consumer/`）、和邻居系统重名但职责不同的包
- 目录名和实际职责不符的，直接点出来——这属于阶段五黑话的一种，越早说越好

### 多仓库时给几棵树

聚焦哪一块在划范围时已经定了，这里按那个结论走，别自己另起一套：

- **聚焦的那个仓**：给完整的树，就是上面这个规格
- **读得到的兄弟仓**：只给**顶层一两层**，每个仓三五行，说清"它大致分几块、你要找的东西在哪一块"。新人这会儿不需要在别人的仓里认路，只需要知道那儿有什么
- **读不到的兄弟仓**：不给树，一行带过——"`inventory-svc`：读不到，只有契约，见阶段二"

**跨仓的同名目录一定要点出来。** 好几个服务都有 `service/order/`，但装的是完全不同的东西——新人搜到一个文件名，很容易打开的是别的仓那份。同名而职责不同的，在树的注释里直接写"注意：`pay-svc` 里也有一个 `service/order/`，那是支付侧的订单视图，不是这里的"。

## 阶段二：对外接口地图

**目标**：让新人知道这个系统"对外承诺了什么"。

- 枚举**全部**入口：HTTP、RPC、MQ 消费者、定时任务 / Job、CLI、Webhook 回调、管理后台、对外 SDK。**和侦察阶段列的清单逐条核对，一个都不能少**
- **按业务领域分组，不是按 controller 文件分组**——文件划分是历史产物，业务领域才是新人的认知锚点
- 明确标出主干和边角。新人最怕平铺直叙、没有重点

输出成表：

| 业务领域 | 客户实际用的地址 | 代码里注册的路由 | 类型 | 谁在调 | 一句话作用 | 代码位置 |
|---|---|---|---|---|---|---|
| 订单 | `POST /v1/orders` | `POST /api/orders` | HTTP | App 端 | 用户下单，核心中的核心 | `order/OrderController.java:42` |
| 订单 | `POST /v1/orders/{id}/pay` | **本仓没有** | HTTP | App 端 | 支付，被网关转去了 pay-svc | — |

**这两列必须分开**，哪怕大多数行两者相同——合成一列，网关改写和被别的服务截胡就永远显不出来，而那正是新人最容易栽的地方。两列的值从下面的反向校验来。

表后补一句：**"如果你只看三个接口，就看这三个"**，并说明为什么。这三个就是阶段四的候选核心链路，按什么标准挑、怎么排序，在那一步展开。

### 反向校验：从用户实际用的地址倒推

上面全是从代码**正推**——枚举仓库里注册了什么。正推有个盲区：它只能看见这个仓库承认的东西，看不见网关改写、看不见被兄弟服务截走的流量。所以再反着走一遍：

> **拿客户文档 / SDK 默认配置 / 前端请求 / 线上日志里的真实地址，逐条打一遍，和代码里的路由对上号。**

三种结果，每种都要处理：

- **对得上** → 这条接口确认无误，标成"实测"
- **对不上：真实地址在代码里找不到** → 请求在到达这个仓库之前就被网关改写了，或者压根被另一个服务接走了。**这是整场导览里最高价值的发现，必须讲**——新人不知道这件事，就会在错的仓库里找错的代码。回到上面那张表，「代码里注册的路由」填「本仓没有」，并在「一句话作用」里写清它去了哪儿
- **对得上但打不通**（404 / 500 / 超时）→ 只能确定"我这次没打通"，不能就此判死。可能是网关没放通、打错了 host、灰度没开、要鉴权而我没带凭据，也可能真是废弃残留。把这几种可能摆出来、标成"推断"，记进待确认清单，别替它下结论

一个好用的技巧：**不同层返回的错误响应文案通常不一样**——网关的 404、Web 框架的 404、业务代码自己写的 404，长得都不同。故意打几个不存在的路径，比对返回体的措辞和 header，就能剥出一个请求实际穿过了几层、每层是谁。这比读任何部署文档都直接。

打之前先看纪律 2 的边界：只打读操作和故意打错的探测，有副作用的接口不要真打。

## 阶段三：分层架构

阶段一的目录树讲的是"东西放在哪"，这一步讲的是"它们之间怎么调"。画**这个项目实际的层**，不是教科书上的四层。用 Mermaid flowchart，要包含：

- **外部依赖**：DB、缓存、消息队列、第三方服务，画在图上
- **跨层调用的规矩**，以及现实中被打破的地方（"理论上 controller 不能直接碰 DAO，但 xxx 这里破例了"）

```mermaid
flowchart TB
    C[OrderController] --> S[OrderService]
    S --> R[OrderRepository] --> DB[(MySQL 订单主库)]
    S --> Cache[(Redis 订单缓存)]
    S --> Risk[risk-engine 风控 - 外部服务]
    S --> OSS[(对象存储 凭证图片)]
    S -.异步.-> MQ[[Kafka order_created]]
    MQ -.-> Con[OrderConsumer] --> ES[(ES 订单索引)]
```

图上的存储要和阶段五那张存储清单**双向对齐**：这里画漏一个，阶段五多半跟着漏；反过来，阶段五翻配置和依赖时经常会捞出这里没画的（只在定时任务里跑的数仓同步是最典型的一个），**捞到就回头把这张图补上**，别让两处各说一套。

图里只放组件名，**不要把路径塞进节点**——节点里挤一堆路径既看不清也放不下说明，路径已经在阶段一的目录树里了。图讲完补一句每个层住在树的哪一支即可。

**这一步只说"有哪些组件、谁调谁"**：为什么选 Kafka、缓存怎么用、那条虚线为什么要做成异步——一律留到阶段七。

## 阶段四：核心链路时序图（业务视角）

候选就是阶段二标出的那三个接口，挑 2–3 条展开。**核心链路 = 业务价值最高的那类请求**，通常同时满足：直接面向终端用户（不是管理后台、定时任务、健康检查）、承载主要业务价值（下单、支付、派单这类公司靠它赚钱的动作）、**并且最复杂**——正因为价值高，历年的需求、边界、优化、事故补丁全堆在它身上。

所以**先讲最复杂的那条划算**：其余基本是它的子集，讲透一条，别的新人能自己看懂。别嫌复杂挑个简单的开场，那只是把困难往后推。

看不出哪条最重要时，从代码里找这三类信号（可叠加，**只用于你自己排序，别讲给新人听**，里面全是技术词）：

- **代码最厚**：分支最多、依赖外部服务最多、事务链路最长、注释里"注意 / 坑 / 历史原因"最密
- **保障最重**：唯一做了降级、限流、熔断、幂等、分布式锁、对账补偿的那条——这些只会加在出事赔钱的链路上
- **被盯得最紧**：单测和集成测试最密、`git log` 改得最频繁、监控告警和压测脚本里点名的那条

拿不准就摆出候选问一句："我看下来 A / B / C 是主干，先从哪条开始？"**选定后排个序**，最核心的第一——阶段六只追第一条。

选定后用 Mermaid sequenceDiagram。participant 用**真实的类名和服务名**（这是回到代码的锚点，不要用"服务A""模块B"），但**箭头上标业务动作，不标技术手段**——写"扣减库存"，不写"调用 Redis DECR"。

**跨出仓库边界的那几跳必须画出来**——新人要能一眼看出这条链哪几步不在自己仓里。**只给跨出去的那个 participant 标归属**，本仓的不标（每个都挂仓名，七八跳的图立刻宽到没法看），图下一句话交代"未标注的都在 X 仓"。读不到的画成黑盒，只标输入输出：

```mermaid
sequenceDiagram
    participant App as App 用户
    participant OrderController
    participant OrderService
    participant InventoryClient
    participant InvSvc as inventory-svc · 别的仓库 · 黑盒
    App->>OrderController: 提交订单
    OrderController->>OrderService: 校验并创建订单
    OrderService->>InventoryClient: 扣减库存
    Note over InventoryClient,InvSvc: 这一跳跨出本仓库
    InventoryClient->>InvSvc: 扣减库存
    InvSvc-->>InventoryClient: 扣减成功 / 库存不足
    InventoryClient-->>OrderService: 扣减成功 / 库存不足
    OrderService-->>App: 返回单号，订单进入"待支付"
```

图下补一句：未标注归属的 participant 都在 `order-api` 仓；`inventory-svc` 读不到，只能从调用方代码看出契约。

每张图后面补充**图上画不下、但属于业务的**信息：

- 这条链路在业务上**从什么诉求开始、以什么结果结束**
- **每一跳的业务职责**，一句话说清它在这条链路里负责哪件事
- **业务分支**：什么条件下会走到不同的路径（新老用户、商品类型、是否命中活动）。新人改需求时踩的坑多半在分支上，而不在主干
- 哪一步是**业务承诺的兑现点**——过了这一步，对用户来说这件事就算办成了

**这一步一个技术词都不要出现**：同步还是异步、事务边界划在哪、超时多久、重试几次、锁怎么加、缓存打在哪——**全部留到阶段七**。

## 阶段五：数据模型与内部黑话

这一段最省新人时间：代码他读得懂，但读不懂"为什么这张表叫 `t_biz_ext`"，而这类困惑没人会主动讲给他听。

### 先列存储清单：这些数据一共存在几个地方

**别默认"数据模型 = MySQL 里的表"。** 最常见的漏法就是：ER 图画得挺漂亮，新人上手才发现同一份数据在 Redis 有缓存、ES 有索引、原始文件在对象存储——改了库不同步别处，线上就出事。所以先把存储列全，一个不落：

| 存储 | 存什么 | 谁写 / 谁读 | 主数据还是派生 | 怎么发现的 |
|---|---|---|---|---|
| MySQL `order` 库 | 订单主数据 | 下单写、多处读 | **主数据** | `db/migration/` |
| Redis | 订单详情缓存、幂等键 | OrderService 读写 | 派生，可重建 | `RedisKeys` 里的 key 前缀常量 |
| ES `order_idx` | 订单搜索索引 | consumer 异步写 | 派生，可能滞后 | ES 客户端依赖 |
| 对象存储 | 用户上传的凭证图片 | 上传接口写 | **主数据**，丢了补不回来 | 配置里的 bucket |
| Kafka `order_created` | 订单创建事件的消息体 | OrderService 发 | 传输中的数据 | 生产者代码 + 消息 DTO |

**"主数据还是派生"这一列最值钱**：派生的能重建，主数据丢了就没了——直接决定新人哪些地方能随手改。

找全靠配置和依赖，比翻代码快：连接串 / bucket 配置、客户端 SDK（Redis / ES / Mongo / ClickHouse）、key 前缀常量类、消息体 DTO、只在定时任务里出现的数仓同步。**这张清单比阶段三那张图更全是常态**（分层图顺主链路画，照不到 Job 里的存储），发现新的就回头补图。

### 关系型部分：先给全集，再挑核心画图

**"覆盖不全"的痛点是新人不知道还有什么，不是每张表都得画图。** 所以分两层：

**第一层，全集清单——一张不落**，每张一行：表名、干什么用的、数据量级、是不是核心。清单很便宜，但它划出边界，也让新人日后自己查得到。

**第二层，挑核心表画 erDiagram。** 判据：被阶段四那几条链路读写的、被多处关联的、承载主要业务量的。挑出来的表之间关系要画全。

**核心字段一个都不能少。** 这里最容易缩水——只挑"新人会误解的字段"讲，结果真正的核心字段反而没露面。每张核心表，下面这几类**必须出现**：

- 主键，以及**对外使用的业务标识**（订单号这种，往往不是主键）
- 关联到别的表的外键 / 关联键
- 状态、类型这类枚举字段，**取值含义逐个列出来**，以代码里的枚举定义为准
- 业务量字段：金额、数量、时长、配额
- 时间戳，并区分**记录时间**（创建 / 更新）和**业务发生时间**（支付时间、履约时间）——这两类混用是新人算错报表的头号原因
- 软删除标记、租户 / 分区键（有的话）

在此之上再标注：容易误解的、名实不符的、**死字段**（全仓库无人写入或永远固定值，直接说"这是死的"）。纯审计和扩展字段一句话带过。兜底判据：**参与核心链路的字段一个都不能漏。**

```mermaid
erDiagram
    ORDER ||--o{ ORDER_ITEM : "一单多行"
    ORDER {
        bigint id PK "内部主键，不对外"
        varchar order_no "对外单号，日志和客服都用它，不是 id"
        tinyint status "1待支付 2已支付 3已完成 4已取消 5退款中"
        bigint user_id "逻辑外键，库上没有约束"
        decimal pay_amount "实付金额，单位元；应付金额在 order_ext"
        datetime created_at "记录创建时间，不是支付时间"
        datetime paid_at "业务发生时间，报表口径用这个"
    }
```

表结构以 **migration / DDL / ORM 实体**为准，字段含义以**实际读写它的代码**为准——注释是数据模型里最容易过期的东西。另外说清**外键是逻辑的还是物理的**：大部分线上库只有逻辑外键，新人以为有约束会写出问题。

**这一步不讲索引怎么建、分库分表、读写分离、缓存和索引怎么保持一致**——那些是阶段七的话题。这里只讲数据存在哪儿、长什么样、字段是什么意思。

**黑话词典** ⭐ 单独成表：

| 黑话 | 到底是什么 | 代码里叫什么 | 对应存储/字段 | 出处 |
|---|---|---|---|---|
| "打标" | 给用户加运营标签 | `UserTagService` | `user_tag.tag_code`；Redis `tag:uid:*` | `tag/UserTagService.java:88` |

要抓的重点：业务缩写、内部代号、枚举里的魔法数字，以及**命名和实际含义不一致的历史遗留**（`is_deleted=2` 表示"已归档"这类）。老员工对这些习以为常，新人必然踩坑。

## 阶段六：一个具体请求的全程追踪（业务视角）

阶段四讲的是一类请求的通用走向，这一步要**落到一次带真实参数的请求上**——差别是抽象层级，两步都还在业务视角里。这是从"听懂了"到"能上手"的关键一跃。

**只追阶段四排第一的那条链路。** 一次追两条会互相干扰，新人分不清哪个细节属于哪条；等他能自己复述这一条，其余的多半已经能自己看懂了。

**这一阶段只讲业务发生了什么，不解释技术选型**——"为什么用缓存、锁加在哪"留到阶段七。

- **参数取自真实来源**：测试 fixture、接口文档示例、日志样本。实在没有就自己构造，但要说明是构造的
- **逐跳讲业务语义**：这一跳收到什么 → 做了什么业务判断（校验了什么、依据哪条规则）→ 读写了哪张表的哪个字段 → 业务状态从什么变成了什么 → 传给下一跳什么
- **跨仓库的那几跳要点名**：请求在这一跳之后离开了这个仓库，去了哪个服务、走什么协议、那边大致做了什么、回来的是什么——这几跳恰恰是新人最容易断片的地方
- **用黑话词典里的词**，并随手带出它对应的字段，把阶段五和这一步缝上
- **收尾缝合数据模型**：请求结束后 DB 里哪几行变成了什么样，Redis / ES / 对象存储跟着变了什么——或者**没跟着变、要等异步补**，这个时间差最坑新人

然后**再跑一个失败/边界变体**（库存不足、用户重复提交、下游没给回应），讲清楚业务上会回退到什么状态、用户看到什么。新人接手的第一个任务多半是修这类 bug，而不是写 happy path。

讲完停一下确认：**用户能不能自己复述一遍这条链路**。能复述，才进入阶段七。

## 阶段七：核心功能的技术架构与方案

到这里新人已经知道这条链路在业务上要达成什么，**现在才有资格评价它是怎么实现的**。反过来讲，不知道业务目标就听技术方案，等于听一堆无法归因的名词。

针对阶段四挑出的那几条核心链路（其中第一条阶段六已经细追过），逐项拆解它的技术方案。常见的着眼点：

- **缓存**：缓什么、key 怎么设计、失效策略、穿透/击穿/雪崩怎么防
- **异步化**：阶段四那条链路里哪几步其实是异步的、为什么要拆出去、消息可靠性和顺序性怎么保证、消费失败怎么办
- **一致性**：事务边界划在哪、**为什么划在这里**（新人写出脏数据的头号原因）、跨服务用的是最终一致还是别的方案、有没有对账和补偿
- **并发控制**：乐观锁 / 悲观锁 / 分布式锁，锁的粒度和 key 是什么，锁失效会发生什么
- **幂等**：幂等键是什么、存在哪、有效期多久
- **稳定性**：限流、降级、熔断、超时和重试策略
- **性能**：索引怎么建的、有没有批量/预计算/读写分离
- **扩展性**：策略模式、配置化、feature flag、规则引擎——这决定了新人加需求时该往哪加

每项讲三件事，缺一不可：**解决什么问题 → 具体怎么做的（附代码位置）→ 代价是什么、什么时候会失效**。只讲前两件，新人会当成标准答案照抄到不适用的地方。

两条硬要求：

- **讲这个项目的实际方案，不是技术科普。** 不要展开"什么是分布式锁"，要讲"这里为什么用 Redis 锁而不是数据库唯一键、锁 key 是订单号、过期 30 秒、超时后会怎样"
- **设计意图和历史包袱要分开说。** 有些方案现在看很怪，是当年的约束造成的。这类原因通常代码里找不到——按纪律 2 处理：能从提交记录或文档里找到就标明来源并声明未经代码验证，找不到就直接说"这里我看不出原因，建议问一下老同事"，不要替它编一个合理解释

最后给一句新人最需要的话：**这块改动时哪些地方不能碰**（去掉某个锁、把某步改同步、加一个非幂等的写操作……），以及为什么。

要不要再补一张技术视角的架构图，**区别不明显就别画**——两张几乎一样的图只会让新人以为自己漏看了什么。区别在于：阶段三那张画**谁调谁**（组件和调用关系），这张画**哪里加了什么保障**（缓存挡在哪层、锁加在哪步、哪一跳异步、失败谁补偿、对账从哪切进来）。节点还是那批节点，但连线和标注讲的是机制不是调用。保障机制就一两处的话，写成文字比画图清楚。

## 阶段八：现在才贴源码

前面所有阶段**不贴大段代码**。到这一步，用户已经有了心智模型，代码才能被"读进去"。

- 每条核心链路挑 1–3 个**关键决策点**，每段 10–30 行——优先挑阶段七里讲过方案的那几处
- 删掉无关分支和日志，保留主干，加上中文注释
- **贴之前先说这段要看的是什么**，贴完说这段的坑在哪
- 剩下的不贴，改为告诉他"想看 xxx 就去 `路径:行号`"

## 反面模式

开讲前和交付前各扫一遍：

- ❌ 贴大段源码代替解释——新人本来就是被代码劝退的
- ❌ 用项目黑话解释项目黑话
- ❌ 讲框架通识（"Spring MVC 的请求流程是…"）而不是这个项目的实际做法
- ❌ 只讲 happy path
- ❌ 面面俱到、不分主次，每个模块都给一段
- ❌ 没读到就脑补用"常见做法"填空，或把 README / 注释里的说法不标来源直接当事实陈述
- ❌ 代码和文档不一致时选了文档，或者含糊过去不提
- ❌ 对外接口只从代码正推、一次都没真打过——路由注册了不等于线上走它
- ❌ 没确认边界就开讲——不知道这个仓是不是系统的全部、这个仓里哪几块才相关，先去用 `map-system`
- ❌ 跨服务的那几跳含糊带过，不说去了哪个服务——新人会在错的仓库里找错的代码
- ❌ 把"数据模型"等同于 MySQL 里的表，漏掉 Redis / ES / 对象存储 / 消息体里那几份
- ❌ 核心表只讲"新人会误解的字段"，主键、业务标识、枚举取值、金额、时间这些核心字段反而没露面
- ❌ 待确认清单里塞自己本来就查得到的东西，或者只写"这块不清楚"、不写查过什么
- ❌ 业务流程还没讲完就夹带缓存、锁、事务、重试——技术方案一律等到阶段七
- ❌ 一口气把阶段零到阶段八全部输出，中间不停
- ❌ 有 artifact 工具却把内容和图直接打在对话里，导致图渲染不出来
- ❌ 把文档一次性写完丢过去就完事——要带着他一段段走，每段停下来确认
- ❌ 把导览笔记写进仓库里

## 特殊情况

**多仓库 / 微服务**：这不是特殊情况，是常态，由 `map-system` 接管——先出组成表、再确认聚焦范围。这里只补一条执行纪律：**不要在多个仓库之间横跳**，选定一个讲透，跨出边界的地方标清楚去了哪儿就行。

**仓库过大**：圈范围的事 `map-system` 已经做完，这里只剩一条——**诚实的局部覆盖 > 虚假的全局概览**，按纪律 1 把没覆盖的目录当场说出来。

**前端项目**：入口是路由和页面；"对外接口"是页面/组件及其调用的后端 API；"数据模型"是全局状态（store）的结构和数据流向；"链路"是一次用户交互到渲染更新的过程。

**只有文档没有代码**：可以讲，但**开头就要把话说明白**——全部内容属于"参考"级别，未经代码验证，随时可能与线上实现不符；并列出最需要拿到代码后优先核对的几个点（接口出入参、枚举字段的取值含义、表结构）。不要因为文档写得详细就默认它是对的。

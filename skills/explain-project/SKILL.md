# 新人项目导览

## 这个技能要解决什么

听众是**刚进组的研发**：他会写代码，但对这个项目一无所知。他的真实困境不是"没有文档"，而是**已有的一切都默认你已经懂了**：文档用黑话解释黑话，代码没有入口线索，老员工三句话带过的地方全是坑。

所以本技能的产出是**一次分阶段、可追问、能听懂的导览**：内容分阶段写进一份 artifact（或落盘文件），对话里带着他一段段走、随时停下来答疑。它同样是一份文档，但不是那种一次性甩过去、写给老员工看的架构文档。

判断标准只有一个：一个昨天刚入职的人，听完能不能说清**一次真实请求跨了哪几个服务、最后落在哪个仓库的哪段代码上、数据怎么流**。

这句话里有两层，缺一层都不算数：先是系统级的"跨了哪几个服务"，然后才是仓库级的"哪段代码"。只答得出后半句，说明他拿到的是一次**仓库**导览，不是**系统**导览——而他要的是后者。

## 四条贯穿全程的纪律

**1. 先读够再开口。** 只读了几个文件就总结架构，会给出看似合理实则错误的结论——而新人**没有能力分辨你错在哪**，误导成本远高于说"我不确定"。覆盖度自检：如果某个体量不小的目录你一行都没看过，要么去看，要么在讲之前明确说"这块我没覆盖"。

**2. 实测 > 代码 > 文档。对外接口，讲之前先打一次。**

README、Wiki、接口文档、需求文档、代码注释都会过期，而且**过期得悄无声息**——写的人不会回来更新，但代码一直在跑。新人被过期文档误导，往往要一两周才发现。所以文档只当线索，结论从代码来。

但代码之上还有一层它读不到的事实：**"代码里注册了这条路由"不等于"线上走这条路由"**——中间可能有网关改写、可能被别的服务截胡、可能这条路由早就 500 着没人管。这类事实读多少代码都推不出来，只能打一次才知道。更麻烦的是**从代码正推还会得出反的结论**：看到仓库里注册着 `/foo/v1/bar`，就以为客户用的是它，实际客户用的是 `/v1/bar`，由网关转过来——新人照着错的地址去调试，会白花好几天。

**只打安全的那种**：读接口、健康检查、故意打错参数或打不存在的路径看错误响应，这些都行；写入、删除、支付、发消息这类有副作用的，不要真打——问用户要一个测试环境，拿不到就只讲代码推断并老实标成"推断"。

**打不了也要说清楚。** 服务在内网、没有鉴权凭据、本地根本跑不起来——这是常态，不是失败。这时候：明说"这条我没能实测"，结论退回"推断"级，并按三件套记进待确认清单（现象 / 我查了什么 / 卡在哪）。最糟的做法是打不了却不吭声，让新人以为这条是验证过的。

- 任何结论**优先从代码得出**，并附 `文件:行号`
- **只有代码里确实拿不到时**（比如历史背景、当初为什么这么设计、外部系统的约定）才引用文档或注释
- 引用参考来源时**必须显式标注来源并声明不可信**，例如："据 README 说 X（未在代码中验证，可能已过期）"、"注释写的是 Y（注释未必与实现同步）"
- 代码与文档矛盾时**以代码为准**；**实测与代码推断矛盾时以实测为准**。两种矛盾都要明确指出来——这对新人价值极高

每个关键结论按可信度分四级标注，让新人自己知道哪些能直接信：

| 级别 | 依据 | 怎么说 |
|---|---|---|
| 实测 ⭐ | 打过真实接口 / 跑过真实流程 | 直接陈述 + 贴响应片段。与代码推断冲突时以实测为准 |
| 可信 | 读到了代码 | 直接陈述 + `文件:行号` |
| 参考 | 只有文档/注释 | 标明出处 + "未在代码中验证" |
| 推断 | 我根据模式推的 | 说明推断依据 + 给出验证方法 |

**3. 没读到就不要当事实说。** 可以给推断，但必须按上表标成"推断"；不能把脑补讲成陈述句。最常见的一种脑补是**拿框架通识替代项目实情**——不要说"Spring Boot 一般是这样"，要说"这个项目实际是这样，见 xxx"。实在没读就直说"这块我没看，需要的话我去读"。

**4. 分段交付，不要倾倒。** 每讲完一个阶段就更新一次产出，然后在对话里停下来问一句"这块清楚了吗，要不要展开某处"，等回应再继续下一阶段。除非用户明确说"一次性给我全部"。

分段指的是**交付节奏**，不是让内容写得少：artifact 里该写多细写多细，新人回头要靠它复习；节制的是一次推给他多少。

## 讲述的主线：需求 → 功能 → 代码

先有业务需求，才有功能，才有代码。所以导览的顺序就顺着这条链往下走，每一段都是上一段的下游：

**（先划范围：系统由哪些代码组成）→ 项目定位与业务目标 →（代码地图：先给一张坐标系）→ 对外接口 → 分层架构 → 核心链路 → 数据模型 → 具体请求 → 技术方案 → 源码**

范围排在最前面，因为它决定后面每一步该读哪些代码。范围划错，后面读得再细都是白读。

倒过来讲——从代码、从模块、从技术栈讲起——新人只能记住一堆孤立名词，因为他不知道这些东西是为了满足谁的什么诉求才存在的。

**阶段五到阶段七一路都是业务视角**：讲流程走向、讲一次真实请求，不解释任何技术选型。技术实现统一集中在阶段八，源码留到阶段九。这个分界要守住——业务线索被技术细节打断一次，新人就得重新接一次。

## 开讲之前：自己先侦察一遍

这一步**不对用户输出**，是你自己的准备工作。**不要一上来就问用户问题**——他找你就是因为他也不知道。先自己看一遍：

| 看什么 | 能得到什么 |
|---|---|
| 构建文件（pom.xml / package.json / go.mod / requirements.txt）、目录树 | 技术栈、模块划分、依赖了哪些外部系统（可信） |
| README、Wiki、产品文档、需求文档 | **只当线索用，不当结论用**：业务背景的主要来源，但可能已过期 |
| **显式声明的入口**：main / Application / 路由注册 / controller 注解 / *.proto / openapi 定义 | 一眼能找到的那部分入口 |
| **最容易漏看的入口**：MQ 消费者、定时任务 / Job、CLI、Webhook 回调、管理后台、对外 SDK | 没人会主动提，却常常是业务核心。两行合起来才是阶段三要交付的入口全集 |
| DB migration / DDL / ORM entity | 业务真相的最可靠来源，比注释可靠 |
| 测试与 fixture | **真实的请求参数**，阶段七的素材 |
| 配置文件、环境变量、feature flag | 系统边界：它依赖谁、被谁依赖 |

上面这张表扫的全是**仓库内部**，而仓库边界 ≠ 系统边界。**侦察真正的第一件事是定范围**——这个仓库是不是系统的全部、这个仓里是不是只有一部分跟系统有关。方法和产出都在阶段零，先把那一步做掉，再回来按上表逐项扫。

一句话贯穿全程：**"代码里没有"有两种可能——你没找到，或者它不在这个仓库。别默认是前者。** 默认前者，就会一直在错的仓库里翻；把后者摆上台面，才会想到去问"是不是还有别的服务"。

侦察完后，给用户一个**导览大纲**（列出阶段零到阶段九各讲什么、预计多少内容）。**这一步只问一个问题**（以下都不算在内：纪律 4 的每段确认、阶段零确认聚焦范围、阶段三为实测索取真实地址或测试环境、阶段五挑链路时的选择题）：

> "你接下来主要负责哪一块？我可以把那条链路讲得更细。"

用户不回答也没关系，按默认深度继续。

### 怎么在有限时间里"通读"圈定范围内的代码

**先按阶段零的组成表把范围圈出来**——不在范围内的子项目和兄弟仓库，一行都不用读。范围之内也不是逐行读完，而是**先骨架后血肉**：

1. 目录树 + 构建文件 → 建立模块心智图
2. 找到全部入口 → 列成清单
3. 从每个**核心**入口顺着调用往下追，直到落到 DB / RPC / MQ 为止，记录调用链
4. 读 DDL 和实体，把数据模型独立还原一遍
5. 拿调用链和数据模型互相验证，对不上的地方就是你理解错了或代码有坑——两种都值得讲

## 产出放在哪里：开讲之前先定好

**这件事在阶段零之前做完，不是收尾工作。** 图能不能渲染直接决定新人看不看得懂，而对话窗口（尤其是终端）大多不渲染 Mermaid——把源码直接打在对话里，等于什么都没给他。

**优先级 1：有 artifact 工具 → 讲解内容写进 artifact。**

- **讲阶段零之前就先把 artifact 建好**，阶段零的内容直接写进去，对话里只说一句"第一部分放好了，看完告诉我"
- **整场导览自始至终只用这一个 artifact**，每讲完一个阶段就更新它，不要每个阶段新建一个
- **所有 Mermaid 图必须在 artifact 里**，对话里一行 Mermaid 源码都不要出现
- 对话里留给：一两句导语、纪律 4 的确认提问、用户追问时的即时回答

**优先级 2：没有 artifact 工具 → 写成 Markdown 文件，存在仓库之外。** 比如仓库的兄弟目录、用户 home 下的笔记目录、或系统临时目录。同样是开讲前就建好、一路追加，写完把**绝对路径**告诉用户，让他用能渲染 Mermaid 的编辑器打开。

不管落在哪里，**结构都照搬阶段零到阶段九的顺序**，末尾加一节**"待确认清单"**（见下）。

**禁止把这份文档写进仓库里**——仓库根目录、`docs/`、`.notes/`、任何位置都不行：

- 这是个人学习笔记，不是项目资产，极易被误提交进版本库
- 污染别人的 `git status` 和 diff，给 review 添麻烦
- 加 `.gitignore` 不是解法，那也是在改仓库

唯一例外：用户**明确要求**把它作为项目文档提交进仓库。这时先确认放哪个目录、要不要走 review，再动手。

### 末尾那一节叫"待确认清单"，不叫"我没覆盖的部分"

**这一节从阶段零就开始攒，不是收尾时才补。** 导览走一遍下来必然积下一堆"我不确定"，它们恰恰是新人入职第一周最该带去问人的东西——但前提是问题写得足够具体，否则新人只能转述成"这块我没看懂"，问了也白问。

攒的时候**区分两种，因为处置方式正相反**：

| 类型 | 判据 | 怎么办 |
|---|---|---|
| **查不到** | 不在任何我能访问的地方：业务目标、当年为什么这么设计、外部系统的口头约定、别人仓库里的实现 | 写进清单让新人去问人。**必须附上"我查过哪些地方"**，否则对方第一反应就是"你搜过吗" |
| **没查** | 我能查但这次没做：某个目录没读、某个接口没打、某张表没看 | **自己去查，不许写进清单。** 把自己能解决的事塞给别人，是在占用比你贵得多的时间 |

分不清属于哪种，就默认按"没查"处理——先去查一次，查完还是不知道，它自然就变成"查不到"了。

清单里每条写三件事，缺一条就没法直接拿去问人：

- **现象**：我看到了什么，附 `文件:行号` 或实测响应片段
- **我查了什么**：读了哪些代码、打了哪些接口、翻了哪些文档、问过哪些搜索
- **卡在哪**：具体哪一步推不下去，以及我猜是什么（标明是猜的）

只写"这块不太清楚"是无效的——新人拿着它没法开口。

## 阶段零：这个系统由哪些代码组成

**先划范围，再讲内容。** 新人手上通常只有一个仓库地址，于是默认"这个仓库 = 这个系统"。这个默认在两个方向上都会错，而且错法相反：

- **系统比仓库大**：后端由好几个仓库拼出来，他手上这个只是其中一块。照着一个仓库讲，讲出来的"全流程"是断的——请求从哪儿来、走到哪儿去，答案在别人的仓库里
- **仓库比系统大**：一个仓里塞着十几个项目，只有一两个跟这条业务线有关。照着整个仓讲，一大半内容跟他无关，还容易把早就没人维护的老项目当成现役系统讲

这两种错都不是"读得更仔细"能避免的——它们是**范围**问题，不是**深度**问题。所以这一步排在最前面：范围定下来，后面九个阶段都在这个范围里进行。

### 从他手上那一个入口倒推

新人手里一般只有一样东西：一个仓库地址、一个服务名、一个域名或接口地址、或者一条告警。从这一个点往两个方向扩。

**往外扩——找出系统的其他部分：**

- **出站配置**：所有 host / endpoint / url / appkey 类配置项，指向的都是仓库外的依赖。通读一遍配置文件和环境变量，比读任何架构文档都快
- **MQ topic / 队列名**：名字里带着别的服务名的（`xxx_file_transfer` 这种），对面多半就是个兄弟仓库
- **注释和常量里点名的兄弟仓库**：代码里偶尔直接写出另一个服务的仓库名或服务名，拿产品线的服务名前缀 grep 一遍往往能捞到
- **org / team 的仓库列表**：`gh api /orgs/<org>/teams/<team>/repos`，或直接在代码托管平台上按团队筛——一眼看清这条产品线到底有几个服务

**往内收——判断这个仓里哪几块才属于这个系统：**

- **构建描述符有几个**：多个 `pom.xml` / `go.mod` / `Cargo.toml`，或 `package.json` 里的 workspaces、`BUILD` 文件——每一个通常对应一个能独立部署的单元
- **流水线和部署配置里真正被部署出去的是哪几个**：`.gitlab-ci.yml` / `Jenkinsfile` / `Dockerfile*` / `k8s/` / `deploy/` 里出现的服务名和镜像名是最硬的证据——没进流水线的目录多半是死的
- **哪些子目录有自己的入口**：main / Application / 路由注册
- **`CODEOWNERS` / `OWNERS`**：哪些目录归你们团队，直接决定新人该关心哪几块
- **`git log` 近一年动过的才是活的**：几年没提交的子项目别当现役系统讲，但要在组成表里标一句"已停更"，免得新人自己翻到时误以为是主线
- **从线上服务名 / 镜像名反查目录**：拿部署平台上看到的服务名回仓库里搜，能直接锁定它由哪个子目录构建出来

### 产出：一张系统组成表

这是新人第一眼最需要的东西——他得先知道自己站在哪。

| 仓库 / 子项目 | 属于这个系统吗 | 角色 | 我读得到吗 |
|---|---|---|---|
| `order-api`（你手上这个） | 是 | 对外 HTTP 入口 | ✅ 已读 |
| `order-worker` | 是 | 异步履约，消费 MQ | ✅ 已 clone |
| `risk-engine` | 是 | 风控，别的团队维护 | ❌ 读不到，只能当外部依赖讲接口 |
| 同仓 `legacy-crm/` | **否** | 三年没提交的老项目 | — 不在本次范围 |

表里每一行都要说清**凭什么这么判**（在流水线里 / 有自己的 main / CODEOWNERS 归谁 / 近一年有没有提交），按纪律 2 标好证据级别。判不准的行标成"推断"并记进待确认清单，别硬塞进"是"或"否"。

**读不到兄弟仓库怎么办**——这很常见，权限没开、跨团队、代码在别的平台：

- 能 clone 就 clone，有代码搜索就搜
- 拿不到就把它当**外部依赖**讲：只讲接口契约——调它什么、传什么、返回什么、失败了会怎样。这些从你这边的调用方代码里读得出来
- 同时按三件套记进待确认清单。**不要假装它不存在**，更不要凭服务名去猜它内部怎么实现

### 讲完这张表，确认聚焦范围

一张表是廉价的，深讲是贵的。表给完，问一句：

> "这个系统由这几块组成，你手上的是 X。接下来我按 X 往下讲，还是先把跨服务的主流程串一遍？"

用户不回答就按默认走：**在他手上那个仓库里走完阶段一到阶段九，但凡链路跨出边界，都明确标出去了哪个服务**。这样他既拿到能上手的深度，也拿到系统全貌的骨架。

## 阶段一：这个项目是什么，为谁解决什么问题

阶段零划完了范围，**这里是整场导览在业务上的第一句话，其余所有内容都挂在它下面。** 不知道项目定位就去看代码，新人只会一脸懵：每个类都看得懂，合起来不知道在干嘛。

讲清这七件事：

1. **一句话说清它是干嘛的。** 讲不出这一句，说明你自己还没读懂，回去继续读，别硬讲
2. **它在阶段零那张组成表里的位置**：上游是谁在调它、下游它依赖谁、它从谁手里接活、把结果交给谁。表里其余几块各自干什么，这里一句话带过即可——新人要的是知道自己这块卡在整条链的哪一环
3. **服务什么业务目标 / 看什么指标**：GMV、履约时效、风控拦截率、审核通过率……这决定了代码里哪些逻辑是"不能动的"
4. **使用者是谁**：C 端用户、商家、内部运营、还是其他团队的系统。使用者不同，代码里的取舍就完全不同
5. **如果这个服务挂了会怎样**——理解一个系统重要性最快的方式，也直接告诉新人哪些改动要小心
6. **边界：它不做什么。** 新人最常见的误解就是把邻居系统的职责算到这个项目头上，提前划清能省掉大量困惑
7. **演进阶段**：新建系统 / 稳定运行的成熟系统 / 正在被替换或下线的老系统。这决定新人该抱什么心态去看那些"写得很怪"的代码

**这些信息从哪来（严格遵守纪律 2）：**

- **代码能给的**：服务名、领域模型命名、对外接口集合、依赖的上下游服务、表名——从这些能相当可靠地反推出业务范围和边界
- **代码给不了的**：业务目标、指标、组织背景、历史演进。这些只能从 README / 产品文档 / 需求文档 / 提交记录里拿，**必须标注"据文档说，未在代码中验证"**
- **都拿不到时**：把你从代码反推的结论说出来，明确标为推断，并**按"待确认清单"的三件套格式记下来**（现象 / 我查了什么 / 卡在哪）——这本来就是新人第一天最该问的问题，帮他把问题整理成能直接开口问的样子，比编一个答案有价值得多

讲完停一下。定位没对齐就急着往下走，后面全是白讲。

## 阶段二：代码地图——带注释的目录树

先给新人一张**代码地图**，再讲别的。原因很实际：从下一步开始，你说的每个接口、每个类、每张表都会带一个路径，而新人如果没先见过仓库的骨架，这些路径对他就是一串无意义的字符。目录树是**坐标系**，不是内容——所以它排在业务内容前面并不违背"需求 → 功能 → 代码"的主线。

用带注释的目录树，每一行后面跟一句人话，比任何架构图都更快让人找到东西：

```text
src/
├── api/                  接口层：所有 HTTP 入口都在这，一个业务域一个 Controller
│   ├── order/            订单相关接口 ← 你要改的下单接口在这
│   └── user/             用户接口
├── service/              业务层：核心逻辑都在这，改需求 90% 的时间待在这里
│   ├── order/            下单、取消、改价的业务编排
│   └── inventory/        库存扣减（注意：真正的库存服务在另一个仓库，这里只是调用方）
├── repository/           数据层：一个类对一张表，不写业务逻辑
├── job/                  定时任务，容易被漏看，但对账逻辑在这
├── consumer/             MQ 消费者，异步链路的入口
└── common/               工具和常量，枚举值和状态码在 common/enums
resources/
└── db/migration/         建表和变更脚本，看表结构以这里为准
```

写目录树的几条要求：

- **只列到有意义的那一层就停**，不要把每个文件都铺出来，新人需要的是找得到方向而不是清单
- 注释写"**这里放什么、什么时候会来改它**"，不要写"订单模块"这种同义反复
- **标出容易踩坑的目录**：名字看不出是入口的（`job/`、`consumer/`）、和邻居系统重名但职责不同的包
- 目录名和实际职责不符的，直接点出来——这属于阶段六黑话的一种，越早说越好

## 阶段三：对外接口地图

**目标**：让新人知道这个系统"对外承诺了什么"。

- 枚举**全部**入口：HTTP、RPC、MQ 消费者、定时任务 / Job、CLI、Webhook 回调、管理后台、对外 SDK。**和侦察阶段列的清单逐条核对，一个都不能少**
- **按业务领域分组，不是按 controller 文件分组**——文件划分是历史产物，业务领域才是新人的认知锚点
- 明确标出主干和边角。新人最怕平铺直叙、没有重点

输出成表：

| 业务领域 | 接口 | 类型 | 谁在调 | 一句话作用 | 代码位置 |
|---|---|---|---|---|---|
| 订单 | POST /api/orders | HTTP | App 端 | 用户下单，核心中的核心 | `order/OrderController.java:42` |

表后补一句：**"如果你只看三个接口，就看这三个"**，并说明为什么。这三个就是阶段五的候选核心链路，按什么标准挑、怎么排序，在那一步展开。

### 反向校验：从用户实际用的地址倒推

上面全是从代码**正推**——枚举仓库里注册了什么。正推有个盲区：它只能看见这个仓库承认的东西，看不见网关改写、看不见被兄弟服务截走的流量。所以再反着走一遍：

> **拿客户文档 / SDK 默认配置 / 前端请求 / 线上日志里的真实地址，逐条打一遍，和代码里的路由对上号。**

三种结果，每种都要处理：

- **对得上** → 这条接口确认无误，标成"实测"
- **对不上：真实地址在代码里找不到** → 请求在到达这个仓库之前就被网关改写了，或者压根被另一个服务接走了。**这是整场导览里最高价值的发现，必须讲**——新人不知道这件事，就会在错的仓库里找错的代码
- **对得上但打不通**（404 / 500 / 超时）→ 只能确定"我这次没打通"，不能就此判死。可能是网关没放通、打错了 host、灰度没开、要鉴权而我没带凭据，也可能真是废弃残留。把这几种可能摆出来、标成"推断"，记进待确认清单，别替它下结论

一个好用的技巧：**不同层返回的错误响应文案通常不一样**——网关的 404、Web 框架的 404、业务代码自己写的 404，长得都不同。故意打几个不存在的路径，比对返回体的措辞和 header，就能剥出一个请求实际穿过了几层、每层是谁。这比读任何部署文档都直接。

打之前先看纪律 2 的边界：只打读操作和故意打错的探测，有副作用的接口不要真打。

阶段二的目录树讲的是"东西放在哪"，这一步讲的是"它们之间怎么调"。画**这个项目实际的层**，不是教科书上的四层。用 Mermaid flowchart，要包含：

- **外部依赖**：DB、缓存、消息队列、第三方服务，画在图上
- **跨层调用的规矩**，以及现实中被打破的地方（"理论上 controller 不能直接碰 DAO，但 xxx 这里破例了"）

```mermaid
flowchart TB
    C[OrderController] --> S[OrderService]
    S --> R[OrderRepository] --> DB[(MySQL)]
    S -.异步.-> MQ[[Kafka]]
```

图里只放组件名，**不要把路径塞进节点**——节点里挤一堆路径既看不清也放不下说明，路径已经在阶段二的目录树里了。图讲完补一句每个层住在树的哪一支即可。

**这一步只说"有哪些组件、谁调谁"**：为什么选 Kafka、缓存怎么用、那条虚线为什么要做成异步——一律留到阶段八。

## 阶段五：核心链路时序图（业务视角）

候选就是阶段三标出的那三个接口，从中挑 2–3 条展开。**核心链路 = 业务价值最高的那类请求**，它们通常同时具备三个特征：

- **直接面向终端用户**——不是内部管理后台、定时任务、数据同步、健康检查
- **承载主要业务价值**——下单、支付、派单、投放、发消息这类"公司靠它赚钱"的动作
- **最复杂**——正因为价值最高，历年的需求、边界处理、性能优化、事故补丁全堆在它身上

所以**先讲最复杂的那条是划算的**：其余链路基本是它的子集或简化版，讲透一条，新人再看别的能自己看懂。不要因为嫌它复杂而挑一条简单的开场，那只是把困难往后推。

如果你对业务不熟、看不出哪条最重要，从代码里找这些信号（可叠加判断）。**这些是你自己排序用的依据，不要讲给新人听**——里面全是技术词：

- 代码最厚、分支最多、注释里"注意 / 坑 / 历史原因"出现最密的那条
- 唯一做了**降级、限流、熔断、幂等、分布式锁、对账补偿**的那条——这些东西只会加在出事会赔钱的链路上
- 依赖外部服务最多、事务链路最长的那条
- 单测和集成测试最密集的那条
- `git log` 改动最频繁的目录（能跑就跑一下）
- 监控告警配置、压测脚本里被点名的那条

实在拿不准就把候选摆出来问一句："我看下来 A / B / C 是主干，先从哪条开始？"

**把选定的链路排个序**，最核心的排第一——阶段七只追第一条。

选定后用 Mermaid sequenceDiagram。participant 用**真实的类名和服务名**（这是回到代码的锚点，不要用"服务A""模块B"），但**箭头上标业务动作，不标技术手段**——写"扣减库存"，不写"调用 Redis DECR"。

**跨出仓库边界的那几跳必须画出来并标明归属**：participant 后面注明它住在哪个服务/仓库，跨出去的那一跳单独标注。这是新人理解"全流程"的关键——他要能一眼看出这条链上哪几步根本不在自己手上这个仓库里。读不到的那个服务就画成黑盒，只标输入输出：

```mermaid
sequenceDiagram
    participant App as App（用户）
    participant OrderController as OrderController（order-api 仓）
    participant OrderService as OrderService（order-api 仓）
    participant InventoryClient as InventoryClient（order-api 仓）
    participant InvSvc as inventory-svc（别的仓库，读不到，按黑盒画）
    App->>OrderController: 提交订单
    OrderController->>OrderService: 校验并创建订单
    OrderService->>InventoryClient: 扣减库存
    Note over InventoryClient,InvSvc: 这一跳跨出本仓库
    InventoryClient->>InvSvc: 扣减库存
    InvSvc-->>InventoryClient: 扣减成功 / 库存不足
    InventoryClient-->>OrderService: 扣减成功 / 库存不足
    OrderService-->>App: 返回单号，订单进入"待支付"
```

每张图后面补充**图上画不下、但属于业务的**信息：

- 这条链路在业务上**从什么诉求开始、以什么结果结束**
- **每一跳的业务职责**，一句话说清它在这条链路里负责哪件事
- **业务分支**：什么条件下会走到不同的路径（新老用户、商品类型、是否命中活动）。新人改需求时踩的坑多半在分支上，而不在主干
- 哪一步是**业务承诺的兑现点**——过了这一步，对用户来说这件事就算办成了

**这一步一个技术词都不要出现**：同步还是异步、事务边界划在哪、超时多久、重试几次、锁怎么加、缓存打在哪——**全部留到阶段八**。新人这会儿还没有能挂住这些细节的钩子，讲了也是白讲，还会把业务线索冲断。

## 阶段六：数据模型与内部黑话

这一段最省新人时间：代码他读得懂，但读不懂"为什么这张表叫 `t_biz_ext`"，而这类困惑没人会主动讲给他听。

**Schema：** 用 erDiagram 画核心表（挑 5–15 张，不要全画）。每张表说清楚：干什么用的、主键是什么、关键字段、**谁创建谁更新**（生命周期）。字段注释写"新人会误解的地方"，不是把字段名换个说法：

```mermaid
erDiagram
    ORDER ||--o{ ORDER_ITEM : "一单多行"
    ORDER {
        bigint id PK
        varchar order_no "对外单号，日志和客服都用它，不是 id"
        tinyint status "状态机见下"
        bigint user_id "逻辑外键，库上没有约束"
    }
```

表结构以 **migration / DDL / ORM 实体**为准；字段含义以**实际读写它的代码**为准，不以字段注释为准——注释是数据模型里最容易过期的东西，"这个字段现在已经不用了"往往只存在于老员工脑子里。发现某字段全仓库无人写入或永远是固定值，直接告诉用户"这是死字段"。

**关系：** 一对多 / 多对多，以及**外键是逻辑的还是物理的**——大部分线上库只有逻辑外键，新人以为有约束会写出问题。

**状态机：** 把状态字段的取值和流转画出来。状态机往往就是业务骨架，讲清它等于讲清了一半业务。**每条边标出由谁触发**，取值和流转以代码里的枚举和流转判断为准，不以文档为准：

```mermaid
stateDiagram-v2
    [*] --> 待支付
    待支付 --> 已支付: 支付回调（外部触发）
    待支付 --> 已取消: 超时 Job / 用户取消
    已支付 --> 已完成: 履约完成
    已支付 --> 退款中: 客服或用户发起
```

**这一步不讲索引怎么建、分库分表、读写分离**——那些是阶段八的性能话题。这里只讲数据长什么样、字段是什么意思、状态怎么流转。

**黑话词典** ⭐ 单独成表：

| 黑话 | 到底是什么 | 代码里叫什么 | 对应表/字段 | 出处 |
|---|---|---|---|---|
| "打标" | 给用户加运营标签 | `UserTagService` | `user_tag.tag_code` | `tag/UserTagService.java:88` |

要抓的重点：业务缩写、内部代号、枚举里的魔法数字，以及**命名和实际含义不一致的历史遗留**（`is_deleted=2` 表示"已归档"这类）。老员工对这些习以为常，新人必然踩坑。

## 阶段七：一个具体请求的全程追踪（业务视角）

阶段五讲的是一类请求的通用走向，这一步要**落到一次带真实参数的请求上**——差别是抽象层级，两步都还在业务视角里。这是从"听懂了"到"能上手"的关键一跃。

**只追阶段五排第一的那条链路。** 一次追两条会互相干扰，新人分不清哪个细节属于哪条；等他能自己复述这一条，其余的多半已经能自己看懂了。

**这一阶段只讲业务发生了什么，先不解释技术选型**——"为什么用缓存、锁加在哪"留到阶段八。混在一起讲，新人会在业务和技术两条线之间来回切换，两条都记不住。

- **参数取自真实来源**：测试 fixture、接口文档示例、日志样本。实在没有就自己构造，但要说明是构造的
- **逐跳讲业务语义**：这一跳收到什么 → 做了什么业务判断（校验了什么、依据哪条规则）→ 读写了哪张表的哪个字段 → 业务状态从什么变成了什么 → 传给下一跳什么
- **跨仓库的那几跳要点名**：请求在这一跳之后离开了这个仓库，去了哪个服务、走什么协议、那边大致做了什么、回来的是什么。读不到那个仓库就直说读不到，只讲契约——这几跳恰恰是新人最容易断片的地方
- **用黑话词典里的词**，并随手带出它对应的字段，把阶段六和这一步缝上
- **收尾缝合数据模型**：这次请求结束后，DB 里哪几张表的哪几行变成了什么样

然后**再跑一个失败/边界变体**（库存不足、用户重复提交、下游没给回应），讲清楚业务上会回退到什么状态、用户看到什么。新人接手的第一个任务多半是修这类 bug，而不是写 happy path。

讲完停一下确认：**用户能不能自己复述一遍这条链路**。能复述，才进入阶段八。

## 阶段八：核心功能的技术架构与方案

到这里新人已经知道这条链路在业务上要达成什么，**现在才有资格评价它是怎么实现的**。反过来讲，不知道业务目标就听技术方案，等于听一堆无法归因的名词。

针对阶段五挑出的那几条核心链路（其中第一条阶段七已经细追过），逐项拆解它的技术方案。常见的着眼点：

- **缓存**：缓什么、key 怎么设计、失效策略、穿透/击穿/雪崩怎么防
- **异步化**：阶段五那条链路里哪几步其实是异步的、为什么要拆出去、消息可靠性和顺序性怎么保证、消费失败怎么办
- **一致性**：事务边界划在哪、**为什么划在这里**（新人写出脏数据的头号原因）、跨服务用的是最终一致还是别的方案、有没有对账和补偿
- **并发控制**：乐观锁 / 悲观锁 / 分布式锁，锁的粒度和 key 是什么，锁失效会发生什么
- **幂等**：幂等键是什么、存在哪、有效期多久
- **稳定性**：限流、降级、熔断、超时和重试策略
- **性能**：索引怎么建的、有没有批量/预计算/读写分离
- **扩展性**：策略模式、配置化、feature flag、规则引擎——这决定了新人加需求时该往哪加

每一项都讲三件事，缺一不可：**解决什么问题 → 现在具体怎么做的（附代码位置）→ 代价是什么、什么情况下会失效**。只讲前两件，新人会以为这是标准答案，照抄到不适用的地方。

两条硬要求：

- **讲这个项目的实际方案，不是技术科普。** 不要展开"什么是分布式锁"，要讲"这里为什么用 Redis 锁而不是数据库唯一键、锁 key 是订单号、过期 30 秒、超时后会怎样"
- **设计意图和历史包袱要分开说。** 有些方案现在看很怪，是当年的约束造成的。这类原因通常代码里找不到——按纪律 2 处理：能从提交记录或文档里找到就标明来源并声明未经代码验证，找不到就直接说"这里我看不出原因，建议问一下老同事"，不要替它编一个合理解释

最后给一句新人最需要的话：**这块改动时哪些地方不能碰**（去掉某个锁、把某步改同步、加一个非幂等的写操作……），以及为什么。

如果技术组件较多，可以补一张技术视角的架构图——和阶段四的分层图不同，这张按缓存、消息、存储、外部依赖、一致性保障来组织。

## 阶段九：现在才贴源码

前面所有阶段**不贴大段代码**。到这一步，用户已经有了心智模型，代码才能被"读进去"。

- 每条核心链路挑 1–3 个**关键决策点**，每段 10–30 行——优先挑阶段八里讲过方案的那几处
- 删掉无关分支和日志，保留主干，加上中文注释
- **贴之前先说这段要看的是什么**，贴完说这段的坑在哪
- 剩下的不贴，改为告诉他"想看 xxx 就去 `路径:行号`"

## 反面模式

开讲前和交付前各扫一遍：

- ❌ 贴大段源码代替解释——新人本来就是被代码劝退的
- ❌ 用项目黑话解释项目黑话
- ❌ 讲框架通识（"Spring MVC 的请求流程是…"）而不是这个项目的实际做法
- ❌ 只讲 happy path
- ❌ 面面俱到、不分主次，每个模块都给一段
- ❌ 没读到就脑补用"常见做法"填空，或把 README / 注释里的说法不标来源直接当事实陈述
- ❌ 代码和文档不一致时选了文档，或者含糊过去不提
- ❌ 对外接口只从代码正推、一次都没真打过——路由注册了不等于线上走它
- ❌ 把"仓库里没有"直接当成"系统里没有"，不去想它是不是在兄弟仓库
- ❌ 把整个仓库当成这个系统——一个仓里十几个项目全讲一遍，其中大半跟新人无关
- ❌ 全程只讲手上这一个仓库，跨服务的那几跳含糊带过——新人要的是系统全貌，不是仓库导览
- ❌ 待确认清单里塞自己本来就查得到的东西，或者只写"这块不清楚"、不写查过什么
- ❌ 业务流程还没讲完就夹带缓存、锁、事务、重试——技术方案一律等到阶段八
- ❌ 一口气把阶段零到阶段九全部输出，中间不停
- ❌ 有 artifact 工具却把内容和图直接打在对话里，导致图渲染不出来
- ❌ 把文档一次性写完丢过去就完事——要带着他一段段走，每段停下来确认
- ❌ 把导览笔记写进仓库里

## 特殊情况

**多仓库 / 微服务**：这不是特殊情况，是常态，已经由阶段零接管——先出组成表、再确认聚焦范围。这里只补一条执行纪律：**不要在多个仓库之间横跳**，选定一个讲透，跨出边界的地方标清楚去了哪儿就行。

**仓库过大**：明确说出你覆盖了哪些目录、没覆盖哪些，请用户指定优先领域，再深入。诚实的局部覆盖 > 虚假的全局概览。

**前端项目**：入口是路由和页面；"对外接口"是页面/组件及其调用的后端 API；"数据模型"是全局状态（store）的结构和数据流向；"链路"是一次用户交互到渲染更新的过程。

**只有文档没有代码**：可以讲，但**开头就要把话说明白**——全部内容属于"参考"级别，未经代码验证，随时可能与线上实现不符；并列出最需要拿到代码后优先核对的几个点（接口出入参、状态流转、表结构）。不要因为文档写得详细就默认它是对的。

**图表渲染**：图一律放在 artifact 或落盘的 `.md` 里，用 Mermaid 代码块。只有在既没有 artifact 工具、也没法写文件、只能在对话里讲的情况下，才改用带缩进的 ASCII 结构图——不要在不渲染 Mermaid 的对话窗口里甩一段用户看不见的源码。

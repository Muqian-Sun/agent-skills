# 从零开发一个系统的标准工作流

**最高纲领：不要用「我觉得」「通常」「一般」这类词。不确定的时候就去查权威数据源。**

从零开发没有既有代码兜底，每一个拍脑袋的判断都会一路传进架构和实现里，等发现时已经很难改。所以凡是拿不准的——市场情况、竞品做法、业内常用方案、技术选型——先查，再说。

整个流程分四步，**每一步都要和用户确认后才进入下一步**。用户是产品的主人，这四步里所有"选哪个"都由用户拍板，你负责把选项和理由摆清楚。

## 1. 需求：先站到用户那一边

先从产品用户的角度提出一系列真实需求：

- 假如你是用户，你希望这个产品是什么样子
- 你希望它解决你哪些痛点
- 如果有同类产品，当前这个产品在哪些方面做得好，才会让你选它

## 2. 产品：把需求落成功能

- 把上一步的需求整理好，与用户交互，**确定最终需求列表**
- 从产品经理的角度做充分的市场调研、产品调研
- 根据调研结果设计产品功能，**每个功能都说明它解决了用户的哪个痛点**——产品设计必须是解决用户痛点的，说不出解决哪个痛点的功能就不要加

## 3. 架构：只选契合当前阶段的

产品设计与用户确认后进入架构设计。

- **不要过度抽象、过度设计**，只选契合当前阶段、当前规模的架构模式。要考虑未来的维护迭代，但这不意味着一开始就上非常复杂的架构
- 架构设计要与用户交互，**由用户最终确定选用哪种架构**
- 架构定下后做模块拆分、接口定义，做到高内聚、低耦合、模块语义边界清晰

## 4. 方案：每个功能都要有方案设计

架构与模块划分确定后，落地具体的方案设计。

- 对功能做排期，**每一个功能都要做方案设计**
- 方案设计要去看业内当前常用的实现方案，结合当前业务做取舍，**给出取舍理由，由用户抉择**
- 方案定下后再定**技术选型、边界 case、正常业务流程闭环**——这三点同样由你提出可选项和理由，交用户抉择

以上全部确定完，才进入正式的 vibe coding。

## 反面模式

- ❌ 用户说了一句想法就直接开始写代码
- ❌ 需求、架构、方案、技术选型替用户做了决定，只通知结果
- ❌ 用"一般都这么做""通常用 xxx"代替查证
- ❌ 为了"以后可能用得上"，一开始就上复杂架构
- ❌ 功能说不出解决了哪个痛点

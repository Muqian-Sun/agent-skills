## 验证：通过不是证据，改坏了会红才是

- **新写或修改的断言，必须做一次负向验证**：把被测的东西改坏，确认它真的变红。没做过负向验证的测试，等同于没有测试。
- **负向验证要先断言注入生效**，再看测试结果。注入本身失效时（打错位置、被同名定义覆盖、走不到那条分支），会把「测试抓不住」误判成「测试没问题」。
- **恒真断言自查**：断言里如果重新实现了一遍被测逻辑，它就是恒真的。判据是「把生产代码整个删掉，这条还过吗」——过就是空转。
- **验证的有效期只到被验证对象下一次变更为止**。改了契约、定义、映射表之后必须重跑，不能沿用上一版的扫描结果下「已闭合」的结论。

## 证据：代码是唯一可信来源

- 注释、docstring、README、issue 里的旧数字、上文摘要——都不算证据，最多算线索，要另找**被执行的代码**佐证。
- 源码坐标（行号、路径层数、有没有守卫、函数签名）**当场打开看**，不凭记忆也不凭摘要。
- 别人给的结论同样要核到源码再采信或反驳，包括 reviewer 和其他 agent 的。

## 子 agent：只读任务指定便宜模型

- 子 agent（Task）不传 `model` 时继承主会话的模型。派**只读任务**时显式传 `model`，不靠默认继承。
- 显式选模型时只用 Grok 和 Composer，不用 Claude、GPT、Gemini。
- 只读任务的判据：子 agent 不写文件、不改任何状态，只读取和汇总。
  - 单点查找（某个文件/符号在哪、查一个确定的事实）→ `composer-2.5-fast`
  - 多源交叉、归纳成报告的调研 → `grok-4.7-high`
- 上面两个 slug 不在当前可用列表里时：单点查找改用列表里的 Composer，调研改用列表里的 Grok。不要猜一个列表外的名字，也不要换成别的家族。
- 继承主模型（`inherit` 或不传）的：写代码、改文件、做设计取舍、评审代码找 bug。
- 只读任务用 `explore`（找文件、符号）或 `generalPurpose`（要归纳），并且带上上面的 `model`。
- 为什么可以降级：子 agent 的结论本来就要按「证据」一节核到原始来源再采信，关键结论由主会话复核，便宜模型出错的代价被这一步兜住。
- 为什么要显式写：一次调研类子 agent 要用十几到二十几万 token（2026-10-09 实测 4 个网页调研 agent 各约 17.6–24.5 万），默认全跑在主模型上是不必要的开销。

## 代码分析：AST，不要正则

- 依赖关系、patch 目标、符号引用一律用 AST 解析。正则漏跨行调用、漏别名、漏函数体内的惰性 import。
- 统计任何东西前先确认口径完整：同一件事往往有多种写法（如 `patch("m.f")` 与 `patch.object(m, "f")`），只认一种会系统性数少。
- 分析脚本 **fail-closed**：映射不到、解析失败、重复命中，一律判失败并打印。静默跳过会让结果「更绿」，方向恰好与安全相反。

## 静默失败：退出码 0 不等于做成了

- 「命令没报错」≠「命令做了事」。改了文件名/路径之后，被文档或脚本引用的命令要**真跑一遍看输出**，不只看退出码。
- **只在 fallback 分支才现形的 bug**：默认值被 env 或配置覆盖时，生产和测试都走不到默认分支，写错了不会有任何东西变红。这类必须**覆盖与不覆盖两种情况都验**。
- 静默跳过、静默 skip、静默降级：凡是「没声音」的失败路径，都要有一条测试或一处日志盯着。
- 结构性改动（模块变包、文件改名、入口迁移）会让**语法没错但永远执行不到**的代码出现。测试全绿不代表入口还在。

## 算法

- **有现成的算法就直接用，不要手写**。手写不一定比现成的好，而且错漏百出。
- **要设计通用的算法**，不是针对特定参数或特定案例的算法。
- 只有确实没有现成实现的时候，才自己实现。

## 自我修正

- **驳回别人的担忧之前，先把它复述成一个可执行的判据，再去跑那个判据。** 查了一个相近但不同的问题就宣布「不适用」，比不查更糟——它带来没有依据的确信。
- 发现自己错了就直接改，把事实说清楚即可。不辩解、不反复道歉、不做复盘式自责。

## 改 git 仓库：一律用 worktree 和分支

- **在 git 仓库里改文件之前，先建新分支，再用 `git worktree add` 把这个分支检出到单独目录，改动只写进那个 worktree。** 不在用户当前打开的工作区里直接改，也不 `git checkout` 把当前目录切走。当前工作区经常有未提交改动，切分支会被挡住，或者把这次改动和用户自己的改动混在一起。
- 新分支从当前 HEAD 拉出：`git worktree add -b <branch> <path> HEAD`。未提交的内容留在原来的工作区，不会被带进新 worktree。worktree 放在仓库同级目录，目录名带上分支名，不放进仓库里面。
- 分支名用 `feat/<desc>`、`fix/<desc>`、`hotfix/<desc>`。
- **已经在这次任务自己的 worktree 里、并且当前分支不是 main / master 时，就在这里继续改**，不要再套一层。判据：`git rev-parse --git-dir` 和 `git rev-parse --git-common-dir` 不同，且 `git branch --show-current` 不是 main / master。
- 只读（查代码、跑不改文件的命令）留在当前工作区。要改的文件不在 git 仓库里时，不受这条约束。

## 交付

- **做任何设计之前，先尽可能读全，拿到设计所需要的信息和上下文，再开始设计。不要吝啬上下文。** 少读是为了省窗口，代价是设计基于残缺信息。没读完就出的方案是假想，后面的实现会按这个假想走偏。代码、调用方、已有约定、任务提到的文档，都算要读的上下文。
- **读完之后仍不确定的点，汇总成一次提问，每条都写上为什么不确定、各自意味着什么。** 不要边做边问，也不要一条一条地问。同时给出方案，等用户确认。
- **没有不确定的点、并且方案已经得到用户确认之后，就把任务一次性做完再汇报。** 做的过程中不要停下来汇报进度或中间结论。汇报里写清两件事：当前状态，以及建议的下一步。中途只停两次：汇总提问，和等方案确认。
- 阈值和参数标明来源：由别的量推导的 / 有实测支撑的 / 拍的。拍的要明说，并说清后续靠什么校正。
- 防御分支先问「真实业务下这条走得到吗」。走不到就别写——不可能命中的检查是误导性噪音。
- **能直接改的就直接改，不要在外面套一层兼容**。加参数就改签名、把调用方一起改掉；为一个根本不存在的旧调用者留兼容，是看不见的过度工程。只有旧接口确实被大量调用、逐个改成本很高时，才考虑包装。改完签名或重命名后 grep 全仓确认调用方都改到了——动态语言没有编译器兜底。
- 报告结果要如实：测试失败就贴输出，跳过了就说跳过了，做完并验证过才说做完了。
